# Automated testing

Run the deterministic Windows gate locally from the repository root:

```powershell
.\verify.ps1
```

The script restores packages, rejects High/Critical dependency advisories, builds the complete Release graph with warnings treated as errors, runs tests with public-network proxy variables pointed at a closed loopback port, requires at least one executed test, runs `scripts/check-text.ps1`, rejects static service locators and empty C# catch blocks, and creates a clean local release under `artifacts/release`. The release step builds the installer's payload through the Setup project dependency, validates the required application/native DLL/license/user-document files, checks application and installer versions, loads the SQLite native library from both published payloads and enforces the security baseline, verifies every SHA-256 recorded in `release-manifest.json`, and runs the generated Setup executable through isolated first-install, upgrade, preserving-uninstall, complete-uninstall, and repeated-uninstall smoke checks. The text check strictly decodes tracked first-party text as UTF-8 and rejects replacement characters, Unicode private-use characters, long question-mark runs, and known mojibake fragments. Binary files are excluded by the explicit text-extension allowlist; production source files are not excluded.

`LXMusicAccessible.Tests` starts the same `ApplicationHost` registrations as the desktop app. Its fixture uses a unique temporary data directory and real file-backed SQLite, then removes that directory when the fixture is disposed. HTTP requests must be registered with the rejecting handler; unknown requests fail immediately. Browser/process launches, announcements, speech, and native audio are replaced by recording adapters.

Automated tests must not depend on public network access, the real user profile, an installed browser, speech software, or an audio device. This repository intentionally has no remote CI/CD workflow. Every ticket owner runs `verify.ps1` locally, records the exact stage and test results on its GitHub issue, and does not wait for a remote check.

`LXMusicAccessible.TestConsole` remains a manual diagnostic program. It accesses real services and native libraries, so it is not part of the automated quality gate.

## WPF accessibility semantics

WPF controls use native `Content`, `Header`, `Text`, and `Title` as the accessible name whenever those properties already express the task. `Label.Target` remains useful for focus/access-key association, but it is not an accessible-name source: a real `ComboBoxAutomationPeer` returns an empty Name for a combo that only has `Label.Target`. Inputs without their own native name therefore expose a short task-oriented `AutomationProperties.Name`; dynamic dialog inputs derive that name from their runtime label after removing trailing punctuation. The Name must remain separate from ComboBox Selection or TextBox Value. Do not repeat a platform role in an explicit name: use “搜索”, not “搜索按钮”; use a tab Header, not “搜索标签页”. “播放列表” remains a valid business term and must not be rejected merely because it contains “列表”.

An explicit `AutomationProperties.Name` is reserved for controls with no native name source, such as a composed list, an unlabeled edit, a runtime-labeled input, or a meaningful image. It must be short and role-free. Code-created action controls use `Content` or `Header` instead of a duplicate `SetName`; runtime-labeled inputs may use `SetName` only to expose their current short task label.

Ordinary application controls do not expose operation-teaching `HelpText`, `AccessibleDescription`, or ToolTip-derived UIA descriptions. The platform and screen reader already describe basic navigation and activation, so instructions such as arrow-key browsing, Enter/Space activation, Delete, or application-key menus must not be attached to controls. Workflow guidance belongs in visible content or the user guide. Dynamic errors, progress, and completion continue through live-region announcements. `ItemStatus` is a valid UIA state property, but it is not a reliable substitute for the focused Name: common screen readers did not announce it on the leaf list-item focus path. A short state that is necessary to understand a focused leaf item therefore belongs once in that item's Name, with no duplicate ItemStatus binding. Dynamic focused names must notify their bound Name when the state changes.

`AccessibilitySemanticsTests` scans every application XAML file and code-created application/installer path. It includes positive HelpText/ToolTip probes, negative ItemStatus/LiveSetting probes, requires zero HelpText/description sources, and rejects unnamed interactive controls. STA tests exercise real WPF `ComboBoxAutomationPeer` and `TextBoxAutomationPeer` semantics for all label-target inputs, including dynamic dialog labels, and assert that task Name remains separate from Selection/Value. They also load the production list-item automation bindings into the real `SingleReadListBox`/`ListBoxItemAutomationPeer` path, verify that source trust/enablement, hotkey conflict, and download progress occur once in the focused Name, and verify dynamic Name notifications. Source enable/disable tests separately require the `SourcesChanged` notification that rebuilds the source containers. These deterministic tests do not synthesize keyboard input or launch Narrator, NVDA, or JAWS; those flows remain manual pre-release checks.

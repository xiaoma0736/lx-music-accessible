# LX Music Accessible 全面整改与可发布性恢复规范

## Problem Statement

LX Music Accessible 当前能够构建主应用，但尚不具备安全、可重复、可回归验证的发布条件。全面审计确认了 18 项问题，其中 5 项会直接阻断发布：卸载可能递归删除不属于应用的用户文件；登录诊断可能落盘会话凭据；远程脚本会在缺少可信校验的情况下自动替换并执行；关键状态播报没有真正进入 UI Automation；发布流程无法从干净检出生成可验证安装包。

这些并非彼此孤立的缺陷。应用目前存在两个依赖注入容器、窗口先于基础设施就绪、退出保存不可等待、后台任务与原生资源缺少统一所有者、SQLite 完整性约束与写入语义冲突，以及主窗口承担大量业务编排等底层问题。结构上还保留了一套未被界面使用的 MVVM/Views 实现与多个无调用模块，造成真实架构和目录表达相互矛盾。仓库没有自动化测试防线，发布结果无法证明上述行为不会回归。

本规范的目标是恢复项目的安全发布能力，建立可持续的测试与交付基线，并在不进行一次性重写的前提下，把高风险行为逐步迁移到接口小、行为深、可通过同一接缝验证的模块中。

## Solution

整改分为三个连续阶段交付，每个阶段都产生可运行、可验收的纵向增量。

### 阶段一：封住发布阻断项

- 安装目录和数据目录必须由应用创建并带有不可误认的归属信息。卸载只删除归属可证明的已知内容，拒绝磁盘根目录、用户主目录、系统目录和未归属的现有目录。
- 登录诊断永不记录 Cookie、令牌或其他凭据值，只允许记录经过脱敏的名称、域、存在性、长度、状态码和关联标识。
- 远程脚本不再在启动时自动替换并执行。脚本必须经过可信清单校验、受控暂存、显式启用和可回滚激活；执行环境同时限制网络目标、响应大小、解压大小、执行时间和内存。
- 建立唯一的无障碍播报模块。UI Automation 通知或 Live Region 事件是主通道，TTS 只是可选补充；主窗口和所有次级窗口使用同一实例。
- 修复干净检出发布流程，把安装器、测试、依赖审计和产物冒烟验证纳入同一交付门禁。

### 阶段二：恢复一致性与生命周期

- 只保留一个 .NET Host 组合根。窗口由 Host 创建或通过受控窗口工厂取得依赖，禁止静态 Service Locator 和第二套单例图。
- Host、数据库迁移和最小必需模块就绪后才开放主界面交互；失败时提供可聚焦、可朗读、可恢复或可退出的状态。
- 建立可等待、幂等且有超时的关闭流程：先阻止新工作，再取消并等待后台工作，持久化设置和状态，最后释放 Host、HTTP、取消源、临时文件和原生音频资源。
- SQLite 每条连接启用外键，迁移时清理既有孤儿数据，以真正的 UPSERT 替换删除再插入语义；歌单快照通过单一事务原子替换。
- 列表和组合框的选择只改变本地选择与说明，联网或改变下游状态的操作必须由 Enter、按钮或明确命令激活；过期请求必须可取消且不得抢焦点。
- 安装器采用系统可用的默认目录，并补齐键盘导航、控件语义、错误反馈和读屏信息。

### 阶段三：深化模块并删除伪架构

- WPF 窗口和事件处理器作为 UI 适配器，只负责输入转换、状态呈现、焦点和平台事件；搜索浏览、播放队列、歌词下载、设置快捷键等工作流逐个迁入深模块。
- 不进行全量 MVVM 重写。未被真实界面消费的 ViewModel、空 Views 项目、未解析注册和无调用实现应被删除；只有在绑定状态确实产生杠杆时才引入面向具体工作流的 ViewModel。
- 每完成一个工作流迁移，调用者和测试都只跨越该模块的公开接口，旧的平行实现随同删除，不保留兼容转发层。
- 统一异步任务所有权、取消与错误观测；修复编码损坏的公共说明，使用结构化且默认脱敏的日志，并逐步将编译警告收敛为零。

完成后，项目必须达到以下结果：5 项发布阻断问题全部关闭；既有用户数据可安全迁移；关键工作流可在不启动完整 WPF 界面的情况下回归；干净 Windows 工作区能够构建、测试、审计并生成可安装产物；盲人用户可通过键盘和读屏完成安装、启动、浏览、播放、导入与退出。

## User Stories

### 1. 安全安装目录

作为安装用户，我希望安装器默认选择当前系统实际存在且合适的位置，并把应用放入专属目录，以便不会因为固定盘符或复用已有目录而安装失败或污染其他文件。

验收条件：

- 默认位置不依赖某个非系统盘存在。
- 用户选择父目录时，安装器创建应用专属子目录并写入归属信息。
- 对磁盘根、系统目录、用户主目录或不安全复用目录给出可朗读的拒绝原因。
- 安装失败不会留下可被误认为完整安装的归属状态。

### 2. 安全卸载与数据保留

作为用户，我希望卸载只能删除该安装确实拥有的文件，并能独立选择是否保留个人数据，以便任何无关文件都不会受到影响。

验收条件：

- 删除前规范化并验证目标目录及其归属信息。
- 未归属目录、标识不匹配目录和所有受保护目录一律拒绝递归删除。
- 默认删除采用已知文件清单；无法证明归属的剩余内容被保留并向用户说明。
- 旧版本自定义数据目录不会被原地认领并递归删除，而是安全迁移或保留。
- 重复执行卸载结果一致，不会扩大删除范围。

### 3. 隐私安全的登录诊断

作为通过网页或 Cookie 登录的用户，我希望故障报告能够帮助排查但绝不包含可复用凭据，以便分享日志不会泄露账号会话。

验收条件：

- Cookie、令牌、授权头和凭据片段在日志、报告、异常文本和界面中均不可出现。
- 诊断只记录允许的元数据，并由统一脱敏规则处理。
- 自动化测试使用诱饵凭据扫描所有输出，任何完整值或片段出现都会失败。
- 用户提示明确说明报告不应包含凭据，并告知报告保存位置和删除方法。

### 4. 可信脚本获取与启用

作为使用第三方音源的用户，我希望新脚本在校验来源和内容后由我明确启用，以便应用启动不会静默执行被篡改的代码。

验收条件：

- 启动时不会下载后立即替换或执行远程脚本。
- 随版本提供的脚本或可信清单具有可离线验证的版本、摘要和发布者证明。
- 下载内容先进入暂存区；校验失败、来源变化或内容超限时保持当前已验证版本。
- 启用前展示来源、版本、权限和变化摘要，并要求明确操作。
- 激活为原子操作，失败时自动回退到最后一个已验证版本。

### 5. 受限脚本运行时

作为用户，我希望已启用的第三方脚本也只能使用完成音源解析所需的有限能力，以便恶意或失控脚本不能探测本机网络或耗尽资源。

验收条件：

- 默认禁止 loopback、私网、链路本地地址、非允许协议和重定向绕过。
- DNS 解析前后都执行目标校验。
- HTTP 响应、解压输出、脚本体积、执行时长、语句数和内存都有确定上限。
- 超限、取消和拒绝均返回可诊断但不泄密的失败结果，不拖垮应用。

### 6. 可靠的无障碍状态播报

作为读屏用户，我希望登录、导入、加载、播放和错误状态都通过标准 UI Automation 被感知，以便不依赖视觉变化判断操作是否完成。

验收条件：

- 所有窗口通过同一播报模块发送通知。
- 更新 Live Region 后实际触发对应 UI Automation 事件，并在 UI 线程执行。
- 重复高频消息按明确规则合并，关键错误和完成消息不得丢失。
- 没有 TTS 或 TTS 失败时，UI Automation 通道仍然有效。
- NVDA 和 Narrator 能在键盘流程中感知关键状态；JAWS 在可用环境中纳入人工验证。

### 7. 可预测的键盘浏览

作为盲人用户，我希望方向键移动选择时只浏览当前列表，只有明确激活才发起网络工作或改变其他区域，以便不会因探索内容而产生延迟、焦点跳转和多余播报。

验收条件：

- 分类、歌单、排行榜和音源选择均不因 SelectionChanged 自动联网。
- Enter、按钮或等价命令只触发一次明确操作。
- 新操作取消旧请求，旧结果不得覆盖较新的选择。
- 加载状态可朗读，完成后焦点遵循用户发起操作前的约定，不被无条件移到第一项。

### 8. 原子歌单导入

作为导入个人歌单的用户，我希望导入要么完整成功，要么保留原快照，以便网络或数据库故障不会留下空歌单或半份数据。

验收条件：

- 元数据、旧条目清理和新条目写入位于同一事务。
- 任一点故障都会回滚到导入前状态。
- 重复导入同一快照不会产生重复或孤儿记录。
- 大型歌单使用有界批量操作，数据库提交次数不随歌曲数线性增长。

### 9. 可靠数据库升级

作为已有版本用户，我希望升级后收藏、歌单和设置仍完整一致，以便修复外键问题不会反过来删除有效数据。

验收条件：

- 迁移前创建可恢复备份，并对迁移版本进行幂等记录。
- 既有孤儿记录按明确规则清理或隔离。
- 保存既有歌单不会触发级联删除其歌曲。
- 删除歌单不会留下孤儿条目。
- 迁移失败保持旧数据库可恢复，并给出可朗读错误。

### 10. 有序启动

作为用户，我希望主窗口可交互时核心模块和数据库已经就绪，以便首次操作不会静默无效或触发空引用错误。

验收条件：

- Host 和必需迁移在开放主要交互前完成。
- 可选后台刷新不阻塞启动，但其状态、失败和取消由 Host 管理。
- 初始化失败进入明确的错误状态，支持重试、打开日志位置或安全退出。
- 不存在窗口自行构造第二套依赖图的路径。

### 11. 有序退出

作为用户，我希望退出时设置、快捷键、播放状态和音源变更得到可靠保存，以便下次启动不会随机丢失最近修改。

验收条件：

- 关闭流程可等待、幂等，并拒绝重复并行保存。
- 先停止接收新工作，再取消并等待后台任务，然后保存，最后释放资源。
- 超时策略明确；超时和保存失败会记录并向用户提供可理解反馈。
- 所有长期 HTTP、取消源、临时缓存和原生资源都有单一所有者并在退出释放。

### 12. 可复现发布

作为发布维护者，我希望从干净检出通过一个受控入口生成安装包，以便构建成功真正代表可交付。

验收条件：

- 还原、Release 构建、自动化测试、依赖漏洞审计、发布和安装器构建均在干净工作区运行。
- 安装器显式处于构建图中，载荷生成顺序由构建依赖表达。
- 发布目录在解析前创建，并验证不会指向工作区之外的危险位置。
- CI 保存带版本与摘要的产物，并执行安装、启动和卸载冒烟验证。
- 不允许 High/Critical 依赖漏洞、零测试运行或编译警告被误报为通过。

### 13. 可访问的安装器

作为只使用键盘和读屏的用户，我希望完整完成安装、选择数据保留并卸载，以便产品在进入主应用之前就满足无障碍承诺。

验收条件：

- 所有交互控件具有明确名称、说明、助记键和稳定 Tab 顺序。
- 标签与输入建立语义关联，错误和确认对话框可聚焦并可朗读。
- 无鼠标可以完成安装、取消、卸载和保留数据选择。
- 高 DPI 与常见缩放下内容不截断，默认按钮和取消按钮行为一致。

### 14. 单一组合根与可替换适配器

作为开发者，我希望应用只从一个 Host 组合根取得依赖，并能替换 HTTP、进程执行和播报适配器，以便测试和生产使用同一模块接口而不会产生分裂状态。

验收条件：

- 进程中只存在一个应用依赖图和一份单例状态。
- 窗口不使用静态定位器，不直接创建长期外部依赖。
- 真实适配器和测试适配器遵守相同接口、不变量、排序和错误语义。
- 测试通过组合根启动真实模块图，并能观察公开工作流结果。

### 15. 可维护的真实架构

作为维护者，我希望仓库结构只表达实际运行的架构，并让业务规则集中在少量深模块中，以便一次修复可以覆盖所有调用者。

验收条件：

- 未被界面使用的平行实现、空项目、无调用实现和无订阅事件被删除。
- 主窗口不直接执行数据库、HTTP、脚本、文件删除或退出编排。
- 搜索浏览、播放队列、歌词下载、设置快捷键等工作流分别通过小接口提供完整行为。
- 模块迁移不保留双写、兼容转发或第二份状态机。
- 公开说明为 UTF-8 可读文本，预期降级与真实错误可由结构化日志区分。

### 16. 工单单一代理所有权

作为项目维护者，我希望每张实现工单从领取到关闭始终由同一个专属子代理负责，以便责任、上下文、审查结论和最终提交保持连续，主线只承担编排与进度跟踪。

验收条件：

- 每张工单只创建一个专属子代理；该子代理不得再创建用于该工单的下级代理。
- 同一子代理完成需求读取、实现、回归测试、自我审查、问题修正、最终验证、提交和关闭工单的全过程。
- 工单跨多个回合仍复用同一个子代理身份；不得因暂停、上下文续接或首次验证失败而新建替代代理。
- 主代理只选择无 blocker 的工单、启动或唤醒对应子代理、读取状态并维护进度，不编辑实现文件、不替子代理审查或提交、不代为关闭工单。
- 共享工作区默认一次只运行一张实现工单；当前工单提交且工作区恢复可交接状态后，主代理才启动下一张。
- 工单只有在全部验收条件通过、必要测试完成且最终提交可追溯后才能关闭；阻塞或部分完成不得以关闭代替报告。

## Implementation Decisions

### 模块与接缝

- 采用“深模块”原则：每个模块只暴露调用者完成一个工作流所需的最小接口，并隐藏排序、事务、回滚、取消、重试和资源管理细节。
- 不再为同一行为叠加 Repository、Factory、Manager 等转发接口；参数多或依赖多首先被视为真实耦合证据，通过迁移完整工作流解决。
- 调用者和测试跨越同一个公开接缝。仅为测试需要的变化点保留在模块内部，不把内部适配器泄漏到应用接口。
- 仅在确有生产与测试两个适配器时建立接缝。SQLite 和文件系统优先使用临时真实实现；HTTP、进程执行、UI Automation/TTS 和第三方运行环境使用可替换适配器。
- WPF、SQLite、HTTP、BASS、文件系统和操作系统集成是外围适配器；业务工作流不得反向依赖窗口实例或静态全局状态。

### 组合与生命周期

- Microsoft.Extensions.Hosting 是唯一组合根和生命周期所有者。
- 主窗口、次级窗口和托盘入口通过构造注入或由 Host 管理的窗口工厂获取依赖。
- 启动顺序固定为：建立 Host、验证数据目录、运行数据库迁移、启动必需模块、创建并显示可交互窗口；非必需远程刷新在此后由受控后台任务执行。
- 关闭由单一协调模块执行，具有幂等门、取消传播、有限超时和明确结果。关闭开始时同步捕获不可变 UI 状态，随后收敛后台工作并持久化该快照；Host 只在保存及后台收敛完成后停止。

### 存储归属与删除

- 安装和数据位置始终是应用创建的专属目录。归属信息包含模式版本和随机标识，不能只依赖目录名称。
- 删除策略以归属标识和已知内容清单为正向许可，不以“路径看起来像应用目录”为依据。
- 所有目标先解析为规范绝对路径，再拒绝磁盘根、系统目录、用户主目录、关键已知目录、符号链接/重解析点逃逸和父子目录重叠。
- 旧版自定义目录默认保留；需要迁移时复制或移动到新的专属目录，验证完成后才允许用户单独处置旧数据。

### 凭据与诊断

- 采用默认拒绝的字段级脱敏策略。所有日志和诊断输出先经过同一净化模块。
- 凭据值不可为调试目的部分显示；长度、存在性、域、过期状态和随机关联标识足以支持排查。
- 捕获异常只发生在能够恢复、降级或增加上下文的接缝；不可恢复异常继续传播到统一错误处理，不允许空 catch。

### 第三方脚本信任模型

- 应用随版本携带至少一个已验证、可离线使用的脚本版本，不依赖启动联网才能提供基本能力。
- 在线更新由维护者签名的清单描述来源、版本、内容摘要、权限和兼容范围；公钥随应用发布，清单与脚本来自不同信任要素。
- 在签名更新通道完成前，合规实现是随应用发布固定脚本及其内置摘要，并完全停用在线自动更新；不得用同源下载的普通哈希清单冒充独立信任证明。
- 用户自行导入的本地或网络脚本被视为显式信任内容，但仍受运行时能力限制；信任不会因 URL 相同而自动延续到新内容。
- 暂存、验证、启用、健康检查和回滚属于同一个脚本生命周期模块，窗口只呈现结果与确认。

### 数据一致性

- 所有 SQLite 连接启用外键，所有模式变化具有版本迁移、备份和幂等验证。
- 兼容迁移顺序固定为：先替换危险写入语义，再清理或隔离孤儿数据，然后启用外键，最后运行完整性检查；中途失败从备份恢复。
- 更新实体使用不会隐式删除旧行的 UPSERT 语义。
- 聚合写入通过一个事务接口完成；调用者不得先清空再逐条调用持久化接口。
- 批量写入使用线性复杂度的数据结构和有界参数批次。

### UI 行为与无障碍

- 选择和激活是两个不同动作。选择只更新本地状态；显式激活才允许 I/O。
- 无障碍播报模块负责 UI 线程切换、UI Automation 事件、优先级、合并和可选 TTS 适配器。
- 焦点由发起工作流的 UI 适配器根据书面规则恢复；后台模块不能直接移动焦点。
- 安装器与主应用遵循同一键盘、名称、状态、错误和高 DPI 基线。

### 架构迁移策略

- 不以目录、类名或行数作为完成标准；以窗口不再拥有业务规则和外部资源为标准。
- 优先迁移审计已识别的高风险工作流，再迁移搜索浏览、播放队列、歌词下载和桌面集成。
- 每个工作流在新模块通过行为测试后切换唯一调用路径，并立即删除对应旧实现。
- 现有未使用 MVVM/Views 代码不作为未来承诺保留。需要数据绑定时，以实际调用者驱动小型 ViewModel，而不是恢复平行应用层。

### 工单执行合同

- 父规格负责定义整体结果；每张子工单是唯一实现单元，并绑定一个稳定的专属子代理身份。
- 主代理在派发前记录工单、blocker 状态和基线提交，只把已进入实现 frontier 的工单交给子代理。
- 子代理拥有该工单的全部文件修改权和 Git/GitHub 收尾责任，必须在同一上下文中完成实现、针对规格与仓库规范的自我审查、修正、验证、最终提交、结果说明和 Issue 关闭。
- 自我审查至少检查两条轴：实现是否满足工单规格，以及变更是否符合仓库设计、安全、无障碍和测试规范。审查发现必须由同一子代理修正后重新验证。
- 子代理不得把实现或审查再委派给其他代理。需要继续工作时，主代理只能唤醒原子代理并追加上下文，不能创建第二个代理接替同一工单。
- 主代理不得在子代理工作期间修改其文件、重写其提交或代为完成剩余验收；主代理只维护依赖图、状态和下一张可执行工单。
- 由于代理共享同一工作区，默认串行执行工单。若未来要并行开发，必须先修改本合同并为每张工单提供独立 Git worktree；不得在同一工作树并发修改。
- 子代理关闭工单前必须留下最终提交标识和验证摘要。若权限、外部人工验证或环境条件阻止完成，则保持工单打开并清楚报告 blocker。

### 交付门禁

- CI 的必要门禁为：还原、Release 构建、测试发现与执行、依赖审计、干净发布、安装器产物验证。
- 测试数为零、High/Critical 漏洞、未处理编译警告或无法生成安装器均视为失败。
- 当前脆弱依赖升级或移除后，验证产物中实际加载的 SQLite 版本，而不仅检查包声明。

## Testing Decisions

### 主要测试接缝

自动化测试通过唯一 Host 组合根启动真实应用模块图，并从公开工作流接口验证可观察结果。测试使用临时真实 SQLite 数据库和临时应用数据目录；HTTP、进程执行、播报和第三方脚本外部能力使用受控适配器。测试不直接调用私有辅助方法，也不依赖真实第三方网络。

仓库只建立一个可由标准 .NET 测试命令发现的 Windows 测试工程。首批测试资产限制为 Host 夹具、临时目录/SQLite 夹具、拒绝未知请求的 HTTP Handler、记录型播报适配器和记录型进程适配器；不引入通用 Mock 框架，也不设覆盖率百分比目标。未登记的网络请求立即使测试失败。

WPF 无障碍行为是唯一单独的集成接缝：使用 UI Automation 驱动最小窗口与安装器流程，并辅以 NVDA/Narrator 人工矩阵。

### 必需自动化覆盖

- 存储删除属性测试：受保护根、父子重叠、相对路径、大小写、重解析点、缺失/伪造标识、重复卸载及未知文件保留。
- 凭据泄漏测试：在成功、失败、取消、异常和调试报告路径中注入诱饵 Cookie/令牌，扫描日志、文件和用户消息。
- 脚本生命周期测试：错误签名、错误摘要、来源变化、超限、取消、原子启用、健康检查失败和回滚。
- 脚本沙箱测试：私网/loopback/链路本地、DNS 重绑定与重定向、过大 HTTP/解压内容、超时、语句与内存上限。
- 播报契约测试：UI 线程派发、事件产生、优先级、重复合并、TTS 失败回退及多窗口共享实例。
- 数据集成测试：迁移幂等、外键开启、孤儿清理、UPSERT 保留子项、删除无孤儿、导入故障回滚和大型批量性能上限。
- 生命周期测试：启动前不可交互、初始化失败、重复退出、保存失败、超时、取消传播、后台异常观测和资源释放。
- 交互测试：方向键只选择、Enter 只激活一次、旧请求取消、旧结果不覆盖新状态、焦点不被后台结果抢占。
- 发布测试：从空工作区执行完整流水线，验证安装、首次启动、保留数据卸载、完全卸载和产物摘要。

### 人工验证

- 使用纯键盘完成安装、首次启动、搜索浏览、播放、网页登录失败、歌单导入、设置与退出。
- 至少使用 NVDA 和 Windows Narrator 验证焦点顺序、控件名称、忙碌/成功/错误播报和 Live Region；JAWS 在具备许可的环境中验证。
- 在 100%、150% 和 200% 缩放下检查安装器和关键对话框。
- 对真实音频设备切换、BASS 资源释放和第三方平台兼容性保留发布前冒烟验证，不纳入确定性 CI。

### 回归与替换原则

- 新模块接口测试建立后，删除只覆盖旧浅模块内部实现的重复测试或手工脚本。
- 每个修复必须先添加能在旧实现上失败的回归用例；安全删除、凭据脱敏、数据库迁移和脚本校验不得仅靠人工验证。
- TestConsole 不再承担自动化测试职责；仍有价值的诊断场景迁入测试工程或明确标记为人工工具，否则删除。

## Out of Scope

- 新增音乐平台、播放功能、云同步或商业化能力。
- 跨平台移植、WPF 框架替换或整套视觉设计重做。
- 一次性把所有界面改写为 MVVM，或仅为满足某种目录结构而增加抽象层。
- 保证第三方音乐平台、外部脚本源或网络长期可用。
- 在没有证据表明现有引擎无法满足约束前，替换 BASS、Jint 或 SQLite。
- 以单一代码行数目标替代模块接口、所有权和行为验收。
- 对历史已外泄凭据进行远程轮换；规范只负责停止继续泄漏并提示受影响用户自行注销或轮换。

## Further Notes

- 在阶段一全部完成并通过干净发布门禁前，仓库应视为不可正式发布。
- 数据迁移、目录迁移和脚本激活必须设计回滚路径，并在任何破坏性操作前保留可恢复状态。
- 后续实现工单应引用本规范及对应审计发现，采用纵向工作流切片，并显式声明 blocker；总规范本身保持开放，用于追踪整体完成度。
- 后续开发严格执行“一张工单、一个专属子代理、一次完整交付”的所有权合同；主代理不进入实现路径。
- 需要真人读屏验证的交付项应明确标记为人工门禁，但不能替代可自动验证的 UI Automation 事件测试。
- 完成定义不是“代码已移动”，而是旧风险被回归测试覆盖、生产只剩一个调用路径、资源有清晰所有者、发布门禁能够阻止回归。

# LX Music Accessible 全面代码审计报告

**项目：** LX Music 无障碍版 2.0
**范围：** 整个仓库（应用、核心 API、服务、数据、音频、ViewModel、安装器、发布脚本、文档）
**日期：** 2026-08-23
**审计方法：** smell + ponytail-audit + accessibility baseline + WinForms accessibility
**代码规模：** 114 个受审文件，约 26,257 行 C#，115 个 Git 跟踪文件

## 一、结论摘要

项目是一个 Windows 专用的 WPF 模块化单体：`App` 负责界面和组合根，`Services` 负责编排，`Core` 负责各音乐平台 HTTP API 与脚本源，`Data` 负责 SQLite，`Audio` 包装 BASS，`Models` 共享数据结构。项目引用关系没有发现循环，SQL 大多参数化，登录凭据落库使用 DPAPI，下载文件名也做了清理；这些基础做法是正确的。

但当前“分层/MVVM”主要停留在项目名称上。实际产品逻辑集中于 4,855 行的 `MainWindow.xaml.cs`，4 个 ViewModel 没有任何 UI 消费者，`Views` 工程为空。更重要的是，审计确认了 5 个 Critical：卸载可能递归删除用户无关文件、Cookie 调试报告泄露凭据片段、启动时自动获取并执行无完整性保护的第三方脚本、核心无障碍播报链路不可靠，以及发布脚本无法在干净检出上运行。

当前不适合直接发布。建议先修复“删除边界、Cookie、远程脚本、播报、发布链路”五项，再处理双 DI 容器、数据事务与退出保存，最后决定保留 code-behind 还是恢复真正的 MVVM。不要先做大规模目录重构；先封住数据损失和安全边界。

## 二、实际运行链路与项目结构

```text
App.OnStartup
  ├─ 单实例 / 卸载分支
  ├─ 先 new MainWindow().Show()
  ├─ 构建 Host DI 容器
  ├─ 初始化 SQLite
  ├─ 后台刷新第三方脚本源
  └─ MainWindow.InitializeServices(host.Services)

MainWindow (实际应用层，4,855 行)
  ├─ 搜索 / 分类歌单 / 排行榜 / 收藏 / 导入
  ├─ 播放队列 / 换源 / 歌词 / 下载
  ├─ 快捷键 / 托盘 / 设置 / 数据目录
  └─ UIA 实时区域 / TTS / 自定义 AutomationPeer

Services
  ├─ MusicSourceService -> Core 中 5 个平台 API + Jint 脚本源
  ├─ MusicPlayerService -> AudioPlayer(BASS)
  ├─ PlaylistImportService -> 各平台 Provider -> DataService
  └─ Download/Lyric/TTS/Hotkey/DataStorage

DataService -> SQLite + Dapper + DPAPI

另一路（问题）：多个子窗口 -> 静态 ServiceProvider -> 第二套独立服务图
```

| 预期边界 | 实际情况 | 状态 |
|---|---|---|
| App 只做组合与 UI | 主窗口承载几乎全部用例和状态 | Warning |
| 单一 DI 容器拥有单例生命周期 | Host 与静态 `ServiceProvider` 并存 | Critical/Warning |
| View -> ViewModel -> Service | UI 不使用任何 ViewModel，直接调用服务 | Warning |
| SQLite 外键维护聚合完整性 | 未启用 `foreign_keys`，注释与行为相反 | Warning |
| 所有状态播报可被读屏感知 | 一条链路只写日志，LiveRegion 不发事件 | Critical |
| 发布脚本可从干净检出产物 | 首行阶段即因目录不存在失败 | Critical |

## 三、按严重度汇总

### Critical

1. 卸载器对安装目录和自定义数据目录执行无归属验证的递归删除，可能删除用户无关文件。
2. 网页登录失败会把每个 Cookie 的前 24 个字符（短 Cookie 为完整值）写入明文报告，并引导用户发送给开发者。
3. 每次启动自动下载并替换第三方 JavaScript，随后在带任意 HTTP/压缩/加密桥的 Jint 中执行，无签名、哈希固定或内存上限。
4. 次级窗口的 `IAccessibilityService.Announce` 实际只写日志；主窗口 LiveRegion 更新也未发 `LiveRegionChanged`，核心读屏承诺不能可靠成立。
5. `build_release.ps1` 在干净检出上立即失败，安装器又不在解决方案内，交付链路不可复现。

### Warnings

6. 两套 DI 容器造成单例状态分裂和资源生命周期失控。
7. SQLite 外键未开启，同时使用 `INSERT OR REPLACE`，当前留下孤儿，未来直接开外键又会引入级联数据丢失。
8. 歌单导入先清空再逐条插入且无事务，失败会留下空/半个快照，并形成 O(n) 次独立写事务。
9. 退出保存是 `async void` 且没有等待，Host 可能先被停止/释放，设置和音源变更可能丢失。
10. 列表选择和组合框选择直接发起网络请求，读屏浏览/方向键移动会执行真实工作。
11. `MainWindow` 是 God Object；UI、状态机、持久化、原生钩子和业务编排高度耦合。
12. 约 1,900 行结构性死代码/空壳工程长期与真实实现分叉。
13. 没有自动化测试项目或 CI；`dotnet test` 实际运行 0 个测试。
14. NuGet 审计发现两个 High 漏洞依赖，且项目显式固定旧版 `System.Text.Json`。
15. 多个 fire-and-forget 任务、未处理的编译警告和未释放的 `HttpClient`/CTS/预缓存文件形成竞态与泄漏风险。
16. 主窗口在服务与数据库就绪前已经显示，可交互控件能进入空服务路径。
17. WinForms 安装器没有显式无障碍名称/TabIndex，且默认硬编码到 `D:` 盘。

### Suggestions

18. 多处接口注释已经变成乱码/问号，大量空 `catch` 使诊断信息丢失；应以结构化日志和可预期降级替代。

## 四、详细发现

### F-01：卸载边界可删除整个用户目录

- **类别：** Correctness / Security / Destructive action
- **严重度：** Critical
- **位置：** `src/LXMusicAccessible.Data/AppDataPaths.cs:20`、`src/LXMusicAccessible.App/MainWindow.xaml.cs:1149`、`src/LXMusicAccessible.App/App.xaml.cs:315`、`src/LXMusicAccessible.App/App.xaml.cs:324`、`src/LXMusicAccessible.Setup/Program.cs:90`
- **证据：** 自定义数据目录只要求是绝对路径，设置页允许选择任意现有文件夹；卸载时对该路径直接 `Directory.Delete(dir, recursive: true)`。安装器也允许直接选任意目录，应用卸载时把 `AppContext.BaseDirectory` 整棵删除。
- **影响：** 用户若把“文档”“下载”、盘符根目录或已有软件目录选为数据/安装目录，确认“删除用户数据”后会删除同目录内所有无关文件。便携版以 `/uninstall` 启动时也存在相同危险。
- **建议：** 数据与安装都必须落在应用创建的专属子目录；创建不可伪造的归属标记和清单；删除前 canonicalize 路径并拒绝盘符根、用户目录、系统目录、现有非空非归属目录。优先只删除已知文件，而不是递归删目录。
- **第一步：** 立即禁用对自定义根目录的递归删除，只删除 `lxmusic.db`、`logs` 和应用创建的已知文件；安装器强制追加 `LxMusicAccessible` 子目录。

### F-02：Cookie 调试报告泄露会话凭据

- **类别：** Security / Privacy
- **严重度：** Critical
- **位置：** `src/LXMusicAccessible.App/WebLoginWindow.xaml.cs:172`、`:439`、`:590`
- **证据：** 代码通过 DevTools `Network.getAllCookies` 获取包含 HttpOnly 在内的 Cookie；登录失败时逐项把值的前 24 字符写入程序目录。值短于等于 24 字符时完整写出；UI 明确提示“可发给开发者排查”。
- **影响：** 调试报告、备份、客服转发或共享安装目录都可能泄露有效会话片段，直接绕过数据库使用 DPAPI 的保护模型。
- **建议：** 永不落盘 Cookie 值。报告最多包含 cookie 名、是否存在、长度、域和错误码；默认写到受控日志目录，且提示用户不要发送凭据。
- **第一步：** 删除 `preview`/值输出与“发送报告”提示，并在发布前轮换所有曾用于测试的真实会话。

### F-03：远程脚本供应链没有信任边界

- **类别：** Security / Architecture
- **严重度：** Critical
- **位置：** `src/LXMusicAccessible.Core/MusicApi/ScriptMusicSource.cs:31`、`:79`；`src/LXMusicAccessible.Services/MusicSourceService.cs:113`、`:133`；`src/LXMusicAccessible.Services/LxScriptEngine.cs:193`、`:210`
- **证据：** 四个第三方 URL 在每次启动时自动下载并覆盖持久化内容；没有签名、固定 commit/hash、人工确认或回滚验证。脚本在 Jint 中执行，并可调用任意 URL 的原生 HTTP 桥及压缩/加密桥。引擎有 25 秒和语句数限制，但没有内存限制；压缩桥也没有输出大小上限。
- **影响：** 上游仓库、域名、DNS/TLS 终点或维护者账号被攻破后，可让用户机器自动执行恶意逻辑、探测内网/本机 HTTP 服务或触发 CPU/内存拒绝服务。
- **建议：** 默认只执行随版本签名/哈希固定的源；更新走签名清单、固定 commit 和用户确认；限制协议与主机、阻断 loopback/private/link-local，增加 Jint 内存和桥接响应大小限制；保留已验证版本并支持回滚。
- **第一步：** 停止“每次启动自动替换并启用”，改成下载后校验哈希、展示来源变化并等待显式确认。

### F-04：核心无障碍播报链路是伪实现

- **类别：** Accessibility / Correctness
- **严重度：** Critical
- **位置：** `src/LXMusicAccessible.Services/AccessibilityService.cs:22`；`src/LXMusicAccessible.App/PlaylistImportView.xaml.cs:61`；`src/LXMusicAccessible.App/WebLoginWindow.xaml.cs:48`；`src/LXMusicAccessible.App/MainWindow.xaml.cs:264`；`src/LXMusicAccessible.App/MainWindow.xaml:783`
- **证据：** `AccessibilityService.Announce` 只记录日志，注释仍写着“实际应用中需要调用屏幕阅读器 API”，但歌单导入、网页登录、二维码、说明窗口都依赖它。主窗口只是修改 `LiveRegion.Text`，没有取得 AutomationPeer 并触发 `AutomationEvents.LiveRegionChanged`。
- **影响：** 登录失败、导入进度、章节跳转等动态状态对盲人用户可能完全不可感知。微软 WPF 指南明确要求更新文本后抛出 `LiveRegionChanged` 事件。
- **建议：** 建立唯一 `IAccessibleAnnouncer`：UIA Notification/LiveRegion 为主，TTS 为可选补充；所有窗口注入同一实例并在 UI 线程发事件。加 UI Automation 集成测试和 NVDA/讲述人人工矩阵。
- **第一步：** 让 `AccessibilityService` 真正触发 UIA 事件，并把次级窗口接到 Host 的同一个实例。

### F-05：发布链路在干净检出上不可运行

- **类别：** Deployability / Build
- **严重度：** Critical
- **位置：** `build_release.ps1:15`、`src/LXMusicAccessible.Setup/LXMusicAccessible.Setup.csproj:4`、`src/LXMusicAccessible.sln:6`
- **证据：** 仓库没有 `发布` 目录，脚本在创建它之前调用 `Resolve-Path`，实测立即失败。Setup 不在 `.sln`；独立构建又因缺失脚本才生成的 `payload.zip` 报 CS1566。因此正常 `dotnet build` 无法覆盖安装器。
- **影响：** 发布不可复现，主分支“构建通过”不能证明可生成安装包，安装器中的编译错误和警告长期被绕过。
- **建议：** 先 `New-Item -Force` 发布目录，再做边界校验；把 Setup 纳入解决方案或建立显式 build target；将 payload 生成声明为项目依赖/target，而不是隐含顺序。
- **第一步：** 修正脚本第 15 行之前的目录创建，并在 CI 从空工作区执行完整发布 smoke test。

### F-06：双 DI 容器导致分裂单例

- **类别：** Architecture / Coupling
- **严重度：** Warning
- **位置：** `src/LXMusicAccessible.App/App.xaml.cs:148`、`src/LXMusicAccessible.App/ServiceProvider.cs:14`、`src/LXMusicAccessible.App/PlaylistImportView.xaml.cs:27`
- **证据：** App 使用 Host 容器；子窗口通过静态 `ServiceProvider` 懒建第二个容器。两边各自拥有 `DataService`、`MusicHttpClient`、`MusicSourceService`、TTS 等“单例”；`ServiceProvider.Cleanup` 没有调用点。两边注册表还不一致。
- **影响：** 登录 Cookie、音源、缓存、事件与生命周期不一致；静态容器中的 IDisposable 和原生资源直到进程退出都不会释放；测试无法替换依赖。
- **建议：** 只保留 Host 作为组合根，通过构造函数或 Owner/工厂向窗口传依赖。禁止 Service Locator。
- **第一步：** 将歌单导入相关 Provider 注册进 Host，先改造 `PlaylistImportView` 与 `WebLoginWindow`，然后删除静态容器。

### F-07：SQLite 外键与 `REPLACE` 组合存在完整性陷阱

- **类别：** Data / Correctness
- **严重度：** Warning
- **位置：** `src/LXMusicAccessible.Data/DataService.cs:298`、`:326`、`:379`
- **证据：** 连接字符串没有 `Foreign Keys=True`，也没有执行 `PRAGMA foreign_keys=ON`，但删除方法声称子项会级联删除。`SavePlaylistAsync` 又用 `INSERT OR REPLACE`；SQLite 的 REPLACE 语义是删除旧行再插入。
- **影响：** 当前删除歌单会留下孤儿 `PlaylistItems`。如果以后只开启外键，保存已有歌单可能触发 `ON DELETE CASCADE`，反而删掉全部歌曲。
- **建议：** 开启并测试外键；清理现有孤儿；把 REPLACE 改成 `INSERT ... ON CONFLICT(Id) DO UPDATE`；增加迁移版本与事务。
- **第一步：** 先写回归测试覆盖“保存已有歌单不丢歌曲、删除歌单无孤儿”，再改 SQL。

### F-08：歌单导入非原子且按项写库

- **类别：** Data / Complexity / Reliability
- **严重度：** Warning
- **位置：** `src/LXMusicAccessible.Services/PlaylistImportService.cs:154`、`:173`、`:196`；`src/LXMusicAccessible.Data/DataService.cs:778`
- **证据：** 更新快照时先独立清空，再保存元数据，最后对每首歌执行一次独立 SQL；没有事务。收藏批量写入也在循环中执行 SQL，且 `AddFavoriteSongsAsync` 在循环内 `list.IndexOf`，达到 O(n²)。
- **影响：** 任意中途异常会把旧快照变成空或部分数据；大型歌单导入产生数百次提交，UI 等待时间和 SQLite 锁竞争随歌曲数增长。
- **建议：** 在 Data 层提供单个 `ReplacePlaylistSnapshotAsync`，用一个事务完成 upsert + delete + bulk insert；循环用索引或一次 Dapper 批量参数。
- **第一步：** 将导入聚合操作下沉到 DataService，并用故障注入测试事务回滚。

### F-09：退出保存没有被等待

- **类别：** Async / Data durability
- **严重度：** Warning
- **位置：** `src/LXMusicAccessible.App/MainWindow.xaml.cs:1307`、`:4708`；`src/LXMusicAccessible.App/App.xaml.cs:343`
- **证据：** `OnClosed` 最后调用 `async void SaveSettingsOnExit()` 后立即返回；App 的 `OnExit` 随后停止并释放 Host。WPF 不会等待这两个 `async void` 生命周期覆盖。
- **影响：** 设置、快捷键、歌词偏移和音源状态在退出时可能尚未写完，异常也无法向调用者传播。
- **建议：** 建立可等待的 `ShutdownAsync`，在允许窗口真正关闭前保存，再停止 Host；重复退出要幂等且有超时。
- **第一步：** 把保存方法改为 `Task`，让显式“退出”命令先 await 保存再关闭。

### F-10：选择变化触发网络与焦点副作用

- **类别：** Accessibility / UX / Performance
- **严重度：** Warning
- **位置：** `src/LXMusicAccessible.App/MainWindow.xaml.cs:1765`、`:1800`、`:1829`、`:1914`、`:1943`
- **证据：** 选择分类即请求歌单，选择歌单即请求详情，选择排行榜即请求歌曲，组合框选择音源也立即请求。代码同时自动把下游列表选中到 0。
- **影响：** 盲人用户用方向键探索列表/组合框会发起昂贵网络操作并改变多个区域状态；快速浏览还会产生竞态和读屏噪声。
- **建议：** 选择只更新本地描述；Enter/按钮显式加载。若产品坚持即时加载，至少取消上一个请求、缓存、播报忙碌状态且不移动焦点。
- **第一步：** 先把分类、歌单、排行榜三个 SelectionChanged 改为 Enter 激活。

### F-11：`MainWindow` 是实际上的 God Object

- **类别：** Architecture / Cohesion
- **严重度：** Warning
- **位置：** `src/LXMusicAccessible.App/MainWindow.xaml.cs:38`
- **证据：** 4,855 行、约占全部 C# 的 18.5%；同时管理搜索分页、播放重试、歌词、收藏、下载、脚本源、快捷键、托盘、数据迁移、Win32 键盘钩子、焦点和无障碍播报。
- **影响：** 任一功能修改都可能碰到共享字段和事件顺序；无法在不启动 WPF 的情况下测试关键用例；大量 `async void` 与 fire-and-forget 更难推理。
- **建议：** 不做一次性重写。先抽 4 个高风险用例对象：ShutdownCoordinator、PlaylistSnapshotImporter、AccessibleAnnouncer、PlaybackCoordinator；再按功能拆小 code-behind/controller。
- **第一步：** 从无 UI 依赖的退出保存与歌单事务开始抽取并测试。

### F-12：结构性死代码与伪分层

- **类别：** Dead code / YAGNI / Over-layering
- **严重度：** Warning
- **位置：** `src/LXMusicAccessible.ViewModels/*`、`src/LXMusicAccessible.Views/LXMusicAccessible.Views.csproj`、`src/LXMusicAccessible.Core/MusicApi/EnhancedMusicHttpClient.cs:9`、`src/LXMusicAccessible.Services/HotSearchService.cs:11`、`src/LXMusicAccessible.Models/MusicSourceSelector.cs:9`、`src/LXMusicAccessible.App/MainWindow.xaml.cs:21`
- **证据：** 没有任何 XAML/DataContext 引用 4 个 ViewModel；空 `Views` 项目只被 App 引用；EnhancedMusicHttpClient 没有构造/注册/调用点；HotSearch 只注册不解析；MusicSourceSelector 只被死 ViewModel 使用；App 内 RelayCommand 无调用点。
- **影响：** 约 1,900 行代码与真实 code-behind 实现平行演化，其中仍包含构造函数 fire-and-forget 和 async void 缺陷；项目结构给维护者错误心智模型。
- **建议：** 做明确选择：短期以 code-behind 为事实架构并删除空层；或逐个真实迁移功能到 ViewModel，迁移完成前不要保留两份实现。
- **第一步：** 删除空 Views、未用 HTTP/HotSearch/RelayCommand；对 ViewModels 先归档或加真实 UI 引用，不能继续“注册但不用”。

### F-13：没有可自动运行的测试防线

- **类别：** Testing
- **严重度：** Warning
- **位置：** `src/LXMusicAccessible.TestConsole/Program.cs:10`、`src/LXMusicAccessible.sln`

### F-14：依赖存在 High 漏洞且版本显式钉死

- **类别：** Dependency / Security
- **严重度：** Warning
- **位置：** `src/LXMusicAccessible.Core/LXMusicAccessible.Core.csproj:12`、`src/LXMusicAccessible.Models/LXMusicAccessible.Models.csproj:12`、`src/LXMusicAccessible.Data/LXMusicAccessible.Data.csproj:12`
- **证据：** `dotnet list ... --vulnerable --include-transitive` 报告 `System.Text.Json 8.0.4`（High，修复于 8.0.5）和 `SQLitePCLRaw.lib.e_sqlite3 2.1.6`（High，捆绑 SQLite < 3.50.2）。仓库没有 `[JsonExtensionData]`，因此前者的已知利用条件当前未出现，但显式旧包仍会覆盖框架修复版本。SQLite 包没有该顾问标注的直接 patched version，需要升级 Microsoft.Data.Sqlite/底层 bundle 后复核实际 SQLite 版本。
- **影响：** 自包含发布会把旧组件一起交付；未来新增 JSON 模型或处理被替换数据库时风险会升高。
- **建议：** 删除不需要的显式 `System.Text.Json` 引用或升级到当前受支持补丁；升级 Microsoft.Data.Sqlite 依赖链并在产物中打印/验证 `sqlite_version()`；CI 加 NuGet audit。
- **第一步：** 建分支升级依赖，重跑构建、数据库迁移与 `dotnet list package --vulnerable`。

### F-15：异步与资源生命周期失控

- **类别：** Code / Async / Resource management
- **严重度：** Warning
- **位置：** `src/LXMusicAccessible.Services/MusicPlayerService.cs:24`、`:265`；`src/LXMusicAccessible.Services/DownloadService.cs:53`、`:104`；`src/LXMusicAccessible.Services/LxScriptEngine.cs:20`；`src/LXMusicAccessible.Core/MusicApi/ScriptMusicSource.cs:15`；`src/LXMusicAccessible.App/MainWindow.xaml.cs:4390`
- **证据：** 四个长期服务自行 new HttpClient/CTS，但不实现 IDisposable；播放器预缓存临时文件只在换队列清理；多处 `_ = ...Async()` 不集中观察错误。Release 构建有 10 个警告，包括两个空引用、两个未等待 Task、两个伪异步和从不触发的 `ProgressChanged` 事件；Setup 另有 2 个 nullability 警告。
- **影响：** 快速切歌/退出/重复保存时可能出现旧任务覆盖新状态、临时文件残留、连接与取消源泄漏；空引用在启动竞态下可转为运行时故障。
- **建议：** 使用 IHttpClientFactory 或至少统一拥有/Dispose；后台任务通过受控队列和 CancellationToken；开启 warnings-as-errors 并逐项消除现有警告。
- **第一步：** 为 MusicPlayerService/DownloadService/LxScriptEngine/ScriptMusicSource 增加明确生命周期和退出取消。

### F-16：窗口先显示，服务后初始化

- **类别：** Initialization / Correctness
- **严重度：** Warning
- **位置：** `src/LXMusicAccessible.App/App.xaml.cs:135`、`:198`、`:218`；`src/LXMusicAccessible.App/MainWindow.xaml.cs:191`、`:4394`
- **证据：** MainWindow 在 Host 构建和数据库初始化前 `Show()`；此时 XAML 事件已可响应。多个路径用 null 直接返回，`SaveHotkeys` 则直接解引用 nullable `_dataService`，正是编译器 CS8602 的来源。
- **影响：** 启动较慢或数据库迁移异常时，用户操作会静默无效或抛异常；对读屏用户尤其难判断“正在加载”与“功能坏了”。
- **建议：** 先完成组合与最低限度初始化再显示，或显示不可交互的启动状态并在就绪后原子启用主内容。
- **第一步：** 将 Window 构造纳入 DI，数据库初始化完成后再 Show；脚本刷新可继续后台进行。

### F-17：安装器本身未满足项目的无障碍目标

- **类别：** Accessibility / UX / Portability
- **严重度：** Warning
- **位置：** `src/LXMusicAccessible.Setup/Program.cs:15`、`:90`
- **证据：** 程序化创建的 TextBox、Browse、Checkbox、OK/Cancel 没有显式 `AccessibleName`/`AccessibleDescription`/`TabIndex`，标签没有明确关联；也没有助记键。默认目录硬编码为 `D:\Program Files\LxMusic`，许多目标机器不存在 D 盘。
- **影响：** 用户在安装产品之前就可能无法可靠用读屏理解安装路径和焦点顺序；默认安装可能直接失败。
- **建议：** 使用系统 Program Files/LocalAppData 作为默认值；显式 TabIndex、AccessibleName、键盘助记键和可感知错误；安装目录输入框与标签建立语义关联。
- **第一步：** 补全 5 个交互控件的无障碍属性并用 Narrator/NVDA 键盘走完整安装流程。

### F-18：注释腐坏与吞异常降低可维护性

- **建议：** 统一 UTF-8；仅在可证明可忽略的边界捕获具体异常，并至少结构化记录操作、路径（脱敏）和错误。
- **第一步：** 先修公共接口注释，并为数据保存、卸载、Cookie 报告、原生初始化建立明确日志策略。
